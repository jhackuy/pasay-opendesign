KEY BUSINESS RULES

设计系统同时锁定业务不变量。

1 · 部分付款 ≠ PAID

付款逐笔登记，状态由「已确认金额 vs 应付」实时计算：paid < due → Partial；paid = due → Paid。部分付款永远不错误变成 PAID。

2 · 财务记录 Confirm / Reverse

租金与支出提供「确认 / 逆向」，不提供删除。逆向保留审计痕迹并写入时间线，Owner 专属。

3 · APPROVED ≠ 完成

支出 APPROVED 后自动创建 Owner「付款」任务。没有付款的 APPROVED 永远是待办，首页与任务中心持续可见。

4 · Repair ≠ Expense

维修是运营事件，支出是财务事件。一次维修可关联多笔支出（Repair → Contractor → Expense → Approval → Payment），但状态独立。

5 · Owner 审批边界不可绕过

Secretary 可登记全部日常操作；确认租金、审批/付款/逆向支出仅 Owner。越权操作会被拦截并自动转为 Owner 任务。

6 · 用途与类别分离

Purpose 是真实业务描述（「Replace broken aircon compressor」），Category 用于统计（Repair / Utilities…）。不把 Purpose 强塞进 Category。

7 · 双语不变式

Telegram 群内重要业务消息恒为「中文 + English」；Mini App UI 依用户语言显示；状态芯片恒双标签。

8 · ID 是标识符，不是假链接

支出显示 EXP-0006、任务 T-101、维修 REP-0012，作为稳定标识与跳转锚点，不使用 Telegram hashtag 假链接样式。

VNEXT · OPERATION SYSTEM · PASAY-VNEXT-OPERATION-DESIGN-001

VNext Operation：一条 AI 必须推进到
真实业务结果的链路

独立设计层 · 叠加于冻结基线
VNext 不重做已冻结的组件、字体、颜色、卡片与导航。Operation 是一层新的语义容器，天然复用下方全部成熟组件：card / row / chip / timeline / banner / sheet。业务对象（Property / Tenant / Rent / Expense / Repair）不改动。
A · Business State · 业务状态

反映现实业务本身，只被真实业务事件驱动（登记付款并确认 / 逆向）。可被 Owner / Secretary 操作，但绝不因"提醒已发"或"AI 已工作"而改变。

逾期 · Overdue部分 · Partial已收 · Paid
Rent 示例最小集：UNPAID / PARTIAL / PAID。真实世界多数逾期先停在 UNPAID 直到有到账证据。
B · Execution State · 执行状态（严格互斥）

反映 AI 当前推进状态，互斥、覆盖完整、由 AI 自动推进与维护。与 Business State 正交。Needs you / AI working / Escalated 等一律作为 UI 派生表达，不进入核心数据库状态。

ACTIVEAI/系统当前可继续推进，不依赖新的真人或外部结果
WAITING_HUMAN下一步必须等待指定真人业务结果 → 必有 next_actor + expected_result
WAITING_EXTERNAL必须等待租客/银行/供应商/约定日期等外部结果 → 有 expected_result，通常有 wake_at
VERIFYING已有候选业务结果/Evidence，正在判断是否足够可信
BLOCKED当前无法形成合法可执行的下一步（缺前置条件/数据冲突/权限/系统问题）
CLOSEDOperation 生命周期终止，必须记录合法 close_outcome
边界原则：
· ACTIVE 不含"需人动作"——一旦需要真人产生业务结果即转 WAITING_HUMAN。
· 已明确"需要 Owner 做什么"不是 BLOCKED，而是 WAITING_HUMAN + next_actor=Owner。
· State 表达"当前为什么不能/可以继续推进"；next_actor / next_action / expected_result 表达"具体下一步是什么"。
从 State 拆出的推进属性（不重复造状态）：

Close Outcome + Close Reason

Execution State=CLOSED 只表示 Operation 生命周期结束；进一步区分为什么关闭。CLOSED 不改变真实财务状态，非收集情况必须有授权依据。

close_outcome所需授权 / 依据
COLLECTEDVerified Result = 全款到账（部分付款累计到齐）
WAIVEDOwner/授权决定豁免 → 需记录原因 + 授权人
WRITTEN_OFF坏账核销 → 需 Owner 授权 + 金额依据
ADJUSTED账务调整 → 需核对 + 授权记录
CANCELLED_DUPLICATE重复对象合并 → 需去重依据

红线：Owner 不能通过单纯点击"关闭"改变真实财务状态 —— 关闭只记录 lifecycle 结束；真实账务只由业务事件（登记 + 确认 / 逆向）驱动。

Operation Close vs Domain Truth · 冻结原则
Operation close_outcome 只描述"为什么这个 Operation 生命周期结束"。若 Outcome 会改变真实债权、金额、合同义务或其他业务事实，必须产生合法的 Domain Business Event，由 Domain 对象自身更新真实业务状态。
close_outcome→ 所需 Domain Business Event→ Domain 真实业务更新
COLLECTEDverified payment eventRent truth 更新
WAIVEDauthorized waiver / adjustment eventRent obligation 更新
WRITTEN_OFFauthorized write-off eventDomain accounting / business truth 更新
ADJUSTEDauthorized adjustment eventobligation amount / state 更新
CANCELLED_DUPLICATE仅结束重复 Operation不得改变原始 Rent truth
冻结红线：Operation CLOSED ≠ 自动修改业务对象事实。Operation 的 close_outcome 不能替代 Rent / Expense / Repair 自己的 Domain State / Business Event。不得出现："Operation 已合法 WAIVED，但真实业务对象仍错误显示为普通 UNPAID 且没有对应处置记录"。
